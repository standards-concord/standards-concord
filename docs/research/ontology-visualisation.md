# Visual views of an ontology

What existing ontology tools show, what holds up and what doesn't, and what Concord's Browse tab does instead.

## What the established tools do

| Tool | Main views | Worth keeping | Dated or hard to use |
| --- | --- | --- | --- |
| **Protégé** (desktop) | Asserted and inferred class hierarchy, a "Description" frame per class (equivalent to, subclass of, disjoint with, instances) in Manchester syntax, usage and annotation panels | The hierarchy plus a frame per class is the right core. Showing where a term is used. | Swing UI and dense tabs. Axioms read as logic rather than as "what data can an X have". Graph plugins are add-ons. |
| **WebProtégé** | Hierarchy and form-based entity editing in the browser, per-entity discussion and change history | Collaboration on each term. Forms over raw axioms. | Graph view is limited. Visually old-fashioned. |
| **OntoGraf / OWLViz** (Protégé plugins) | Node-link graph you expand node by node, filtered by arc type | Incremental exploration from one class. Filtering by relationship type. | Static layouts that tangle quickly. Mouse only. No sense of cardinality. |
| **WebVOWL** (VOWL notation) | Force-directed graph: classes as circles sized by instances, properties as labelled boxes on edges, datatypes in yellow, colour codes for external and deprecated terms | Colour and size carry meaning. Datatypes and properties are visible. Filters and a "degree of collapsing" control. | Force layouts jiggle and lose the hierarchy. Circles waste space. Not keyboard or screen reader accessible. |
| **TopBraid EDG / Composer** | Form views, SHACL-driven class views, UML-like diagrams | Shape-centric "what properties does this class have". | Enterprise UI. Heavy to learn. |
| **OWLGrEd, Chowlk, Gra.fo** | UML-style class diagrams: boxes with attributes, associations with cardinalities | The notation data modellers already know. LinkML's generated docs draw the same thing. | Mostly editors or static drawings, not live views of a changing ontology. |
| **OLS (EBI Ontology Lookup Service), schema.org pages** | Term pages with a hierarchy and, on schema.org, a table of every property a type can have, including inherited ones | The schema.org property table is the most readable way to answer "what can an X have", especially for non-ontologists. | Graph views (OLS) are an afterthought. |

## What Concord does

The Browse tab has two views that share the class tree on the left and the term page below. (A third, a WebVOWL-style force-directed **Graph**, was removed on 6 Nov 2026: it drew the same classes as the Diagram in a layout that was harder to read.)

- **Classes.** An accessible tree (WAI-ARIA tree pattern: one tab stop, arrow keys, Home and End, type-ahead, expand and collapse all). Ancestors of the selected class open automatically. A class with several parents appears under each. Each class page now has breadcrumbs for every inheritance path, its subclasses, a schema.org-style **property table** (own properties, then those inherited from each ancestor, with expected type and cardinality from domains, ranges, restrictions and functional characteristics), the relationships that can point at it, and a small **neighbourhood diagram**.
- **Diagram.** A UML-style class diagram, because the ODI works in LinkML and data modellers read UML. Boxes list datatype attributes as `name : type [min..max]`. Object properties are labelled associations with cardinalities. Subclasses point to their parent with a hollow triangle. Layout is layered top-down (parents above children) with dagre, so the hierarchy stays readable. It can show the whole ontology, or a class and everything one or two links away. Attributes, inherited attributes, relationships and subclass links can each be turned off. It's drawn as SVG, so it's sharp at any zoom and can be downloaded.

### Following Astra's UI review (findings 10, 11 and 25)

- The tree starts with only the top-level classes. Object properties, datatype properties and individuals start as collapsed headings with counts, and open on their own when the selected term is in them. Search still covers every category.
- A term page keeps its definition, type, and parent and subclasses (or domain and range) visible, plus any deprecation warning. A class's property table is open by default. Everything else is in collapsed sections with counts: **Logical rules**, **Usage**, **Examples**, **Editorial details** and the neighbourhood diagram.
- In the Diagram view (and the Graph view, while it existed), the term navigation folds into a "Terms" panel so the drawing gets the room, and the selected term opens in a side panel with a close button. Arriving with a class selected shows its immediate neighbours, with **Show entire ontology** one click away. Picking a node on the canvas keeps the current scope. In the Graph, relationship labels showed on the selection's links, or everywhere when the graph was small.

### Following Astra's review of the views (PR #9)

- **Cardinalities follow OWL.** Restrictions build up over every ancestor rather than the nearest one replacing the rest. Qualified constraints ("at most 1 Cat", "at least one Dog") are listed under the type instead of being merged into the overall count, and only bound it when they cover the whole range. Several ranges are an intersection ("Person and Employee"). A property whose inverse is inverse-functional counts as functional. Contradictions (such as min 3 and max 2, or a functional property needing 2 values) are shown as **Conflict**, because no instance could satisfy them. Axioms the table can't summarise are listed under it. The "points here" list uses the same numbers as the class table. Unit tests in `apps/web/src/lib/ontologyModel.test.ts` cover each case.
- **Per-type counts.** Several constraints on the same type combine (`min 2 Cat` and `max 3 Cat` give 2..3 Cats), and each type keeps its own count, separate from the total: with `max 1 Cat` and `some Dog`, the diagram and Cat's "points here" list show 0..1 Cats and 1..* Dogs, while the property allows 1..* values in all. Required values of types that are disjoint with each other, or with the expected type, are counted or flagged. Sub-properties of functional properties are functional. Intersection superclasses such as `Thing and (p min 2)` are split into their parts, and the "not summarised" note shows even for a class with no properties. The table says it summarises the stated axioms and that the consistency check (a full reasoner) is the authority.
- **Speed.** Restrictions are merged level by level up the hierarchy, deduplicated as they go and attributed to the nearest class that states them, so a 400-level hierarchy with ten restrictions per class takes tens of milliseconds rather than seconds. Building the model is linear (cycle detection is one depth-first pass), and the speed tests time construction as well as derivation. The class tree always includes the path to the selected class, however long the list, and paths through a subclass cycle start at the class the tree shows as the cycle's root.
- **Long names.** Diagram titles and attributes wrap inside boxes up to 340 px wide (three rows, then an ellipsis, with the full text kept in the tooltip and accessible name), and the drawing's fit and SVG export bounds cover every box, edge and label. Wrapping and truncation work on whole graphemes, so emoji and flags are never split.
- **SVG and PNG export.** The class diagram downloads as SVG or PNG. Labels are measured as SVG text in the browser (so fallback fonts for CJK, emoji and the like are measured as drawn) and wrapped or truncated to their boxes with a small margin. Nothing is stretched to fit. The SVG keeps plain, searchable text with the diagram's font stack, and embeds every subset of Inter its labels use (Latin, Greek, Cyrillic, Vietnamese and so on), taken from the page's own @font-face rules. Browsers therefore draw it as the page does. Viewers that ignore embedded fonts, such as Inkscape and librsvg, substitute their own and may draw text wider than its box. Characters Inter lacks (CJK, Arabic, Hebrew, emoji) always use the viewer's fonts. The PNG is that same SVG, drawn in the browser. An SVG image loads its embedded fonts some time after it decodes, drawing their text blank until then, and nothing reports when they arrive. So the image carries a small strip below the drawing with one large capital in each embedded face, black on white (a fixed letter that only that face draws, such as H, Ж or Ω). The PNG is drawn, without the strip, once every letter shows. It matches the SVG exactly and looks the same in any viewer. It is twice the drawing's size within a 16,384 px side and 64-megapixel budget. If the browser can't allocate or encode it, the export retries at half the scale, and says so if it still can't. The export waits for the page's fonts and the relayout they cause, then copies the drawing in one step, so the file is one consistent state. The screen keeps Inter's normal ligatures and alternates.
- **Scope stays put.** The Diagram (and the Graph, while it existed) is anchored on `?around=`, separately from the term being inspected (`?term=`). Picking a class or property shows its details without redrawing. **Centre on X** recentres. Choosing a class outside the drawing from the term list brings it into view.
- **Keyboard and screen readers.** The diagram's classes share one tab stop (arrow keys, Home and End move between them), the focused class has a visible ring and is panned into view, and a "Go to details" link jumps to the term panel. Each class's accessible name lists its attributes and relationships, and the relationships are also listed as text under the drawing, linked to their terms.
- **No fading.** Selection and hover use borders and heavier lines. Nothing is made translucent, so text keeps its contrast in both themes (checked with axe in light and dark).
- **Fitting.** Diagrams fit when their container first has a size and when it is resized (so one inside a closed section is fitted when the section opens), and the minimum zoom is low enough for a large drawing to fit.
- **Reduced motion.** The graph didn't animate layouts or recentring when reduced motion was requested.
- **Guidance.** Each view says what it's for: find a term (List), and check what data each class has and how the classes connect (Diagram). (The Graph was for exploring how classes connect; it was removed on 6 Nov 2026.) A diagram of more than 80 classes asks where to start, with the most connected classes as suggestions and "Draw everything anyway".

## Making them modern and accessible

- Pan and zoom follow current canvas tools: drag or scroll to pan, pinch or ctrl/⌘ + scroll to zoom, and +, −, 0 and the arrow keys from the keyboard.
- Every class in the diagram is a button with a descriptive name, reached through a single tab stop. Arrow keys move to the nearest class in that direction, and Enter opens it. The graph canvas has a summary label and points to the diagram and class pages, which hold the same information as text.
- The views follow the light and dark themes. The browser tests run axe on the class page and the diagram, and check that every view fits a phone screen without sideways scrolling. Running axe found the app's `--subtle` grey text failing contrast (3.2:1), so it was darkened to meet WCAG AA everywhere.
- Everything is linked: classes, properties and types in the tables and diagrams all open their term page. The view, selection and diagram scope are in the URL, so a view can be shared.

## Possible next steps

- Inferred hierarchy (from HermiT) next to the asserted one, as Protégé offers.
- Instance counts from example data, to size nodes as WebVOWL does.
- Showing a change request's added and removed terms on the diagram, coloured as a diff.
- Editing from the diagram (drag a new subclass, draw an association) that creates a change request.

# What Concord does

Concord, from the Open Data Institute, is a prototype platform for designing data standards together. Every standard is a strict OWL 2 ontology that is kept logically consistent and FAIR, and the whole lifecycle from a first conversation to a published release runs asynchronously, with AI help at each step.

Try it at [standards-concord.vercel.app](https://standards-concord.vercel.app). Alpha testers start at [/alpha](https://standards-concord.vercel.app/alpha).

- **Gather requirements three ways.** An AI interviewer works through a structured use case and asks for competency questions with example answers. Google Meet transcripts can be uploaded, or a co-facilitator bot can join a live call, invited by email like any other guest, and raise clarifying questions (in the Meet chat, if you want). Coding agents such as Claude Code and Codex connect over MCP, read the ontology and report missing or ill-fitting concepts.
- **Turn requirements into changes.** Use cases are synthesised into a change request with structured edits and SPARQL tests for each competency question. The model never writes RDF directly: it proposes terms, and the server compiles them into validated edit operations.
- **Edit terms where you read them.** Each term in Browse has an Edit button for its label, definition, comment, alternative labels, examples and editorial note, next to Report a problem. An edit becomes an editorial change request (one `updateAnnotations` edit), so it is classified, validated and approved like any other change; nothing reaches the working draft until it merges. The edit records the values it started from, so if another change to the same field merges first it goes back to its author instead of overwriting it, and rewording a definition asks whether the meaning is kept (a change of meaning is reviewed as major).
- **Govern without meetings.** Every change is classified as patch, minor or major by explicit rules (based on OWL versioning practice and gist's semver approach), validated (strict lint, OWL 2 DL reasoning with sparq, FAIR checks, competency questions) and then reviewed under the ontology's governance policy. Policies come from a drop-down of five templates (steward-led, lazy consensus, W3C working group, membership vote, ODI-stewarded) and can be tuned: sign-off counts and roles, review periods, votes with quorum and threshold, vetoes, ODI privilege, ownership and transfer, and what is automated.
- **Invite your working group.** In Governance, open Members and roles, then Invite people. Owners and stewards choose roles, how long the link works and how many people can use it. Copy the link when it is created and send it privately; Concord does not send email or store an invitee's email address. People open it and sign in to join. Existing roles are kept. Invitation links shows uses and expiry, and lets you revoke a link. Only someone with ODI oversight, or a platform administrator, can invite another ODI member; ownership uses Transfer ownership. In demo mode, Add a simulated member still offers the demo personas.
- **Release properly.** Releases take the highest level of their changes, bump the semantic version, stamp `owl:versionIRI`, `owl:priorVersion` and `owl:backwardCompatibleWith` or `owl:incompatibleWith`, and include every format plus a SPARQL migration script for major versions. Each ontology is a git repository (tag per release) that is pushed to GitHub on release when configured.
- **Test real apps against proposed changes.** People building on an ontology connect their app; a [GitHub Action](../actions/app-check) tests it against the ontology each open change request would produce and reports back, so every change shows what it would break. With autopilot on, Concord approves or votes yes for the app's owner whenever their apps pass, so changes don't wait on them.
- **Readable at its own address.** The ontology IRI and every version IRI resolve to a public page in the style of W3C and Widoco vocabulary docs: metadata, a reference entry for every term (anchored by its IRI fragment), the use cases and requirements behind the version, worked examples with answers, queries and downloadable data, release notes and every serialisation. RDF clients get Turtle, JSON-LD, RDF/XML or N-Triples from the same address by content negotiation, or by extension (`/def/<slug>/<version>.ttl`). The page is also written into each release as `index.html`, and w3id.org redirect rules are generated for persistent IRIs.
- **Validate data against it.** Paste or upload RDF on an ontology's *Validate data* page, or open *Check data in a SPARQL endpoint* to check a bounded live sample (with an optional named graph). The browser queries the endpoint directly, so it must allow CORS; no credentials are sent. You can also POST it to the ontology or version address (`curl -X POST https://<site>/def/<slug>/<version> -H 'Content-Type: text/turtle' --data-binary @data.ttl`). The data is checked against the SHACL shapes derived from that version and against the terms it defines, and the answer is a JSON report or, with `Accept: text/turtle`, a SHACL `sh:ValidationReport` (listing the first 1,000 results; the summary counts them all). Turtle, JSON-LD, N-Triples, N-Quads, TriG and RDF/XML are accepted, up to 5 MB (JSON-LD 2 MB) or 25,000 distinct triples (holding at most 8 million characters of IRIs and literals, with IRIs up to 4,096 characters), two at a time and 30 requests a minute per client. The shapes themselves come back from the same address for the SHACL profile (`Accept-Profile: <http://www.w3.org/ns/shacl#>` or `?_profile=shacl`). Agents get the same check from the MCP `validate_data` tool.
- **Query it in the browser.** The Query tab loads the ontology into [sparq](https://github.com/sparq-org/sparq), a SPARQL engine compiled to WebAssembly, to run SPARQL and check instance data against the ontology's SHACL shapes without a round trip to the server.
- **See it, not just read it.** The Browse tab has an accessible class tree with schema.org-style property tables, a UML-style class diagram (attributes, relationships with cardinalities, subclasses) and a network graph. See [ontology visualisation](research/ontology-visualisation.md).
- **View it your way.** Turtle, LinkML, JSON-LD, RDF/XML, N-Triples, Manchester syntax and SHACL shapes, also in the much more readable SHACL compact syntax (SHACLC).
- **Use it in code straight away.** Every SHACL shape is also a JavaScript class, generated with the [ODI SHACL converter](https://github.com/theodi/shacl-shape-converter-typescript) over [@rdfjs/wrapper](https://github.com/rdfjs/wrapper). Apps import them from the ontology's own address (`import { VolunteeringDataset } from "https://…/def/volunteering/1.0.0.js"`, or `Accept: text/javascript`), get types from `.d.ts`, or `npm install https://…/def/volunteering/1.0.0.tgz`. The package name is the same for every version and fork, so moving an app from a fork to a release only changes that URL.
- **Identity and private data.** Sign in with Google or GitHub. A WebID and a Solid pod are created automatically; private material such as interview transcripts is stored in the pod, and only the structured, public parts are shared.
- **Alpha testing built in.** `/alpha` walks testers through the platform in a role of their choice with a simulated working group around them, and `/feedback` is a voice-enabled feedback chat with guided and open pathways.
